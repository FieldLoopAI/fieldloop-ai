# FieldLoop

A contractor onboarding/management platform, building toward a voice-first field service system ("FieldLoop AI"). This repo currently holds two web apps; a third component — a native Flutter mobile app for technicians — is being built separately by another developer, informed by this repo's backend/schema but not yet part of this codebase.

1. **Registration Dashboard** (`/staff/login`, `/staff`) — internal tool for FieldLoop staff (`admin`/`onboarding`/`finance`/`support`/`jenex_dev`) to onboard contractors through an 8-step wizard. Fully wired to real Lambda + Supabase, tested end-to-end (API-level + real browser via Playwright) across all 5 staff roles.
2. **Contractor Command Dashboard** (`/`, `/dashboard`) — contractor-facing product. Login/identity, technician roster management (Section 3 — add/edit/deactivate, phone-based accounts, technician setup via an in-app code or a web-link fallback — see HANDOFF.md §21.2), job dispatch (Section 1 — create/assign jobs, real customers/technicians, schedule-conflict detection, service addresses geocoded to `service_lat`/`service_lng` via Google Maps for future geofencing, plus voice-to-job-schedule: speak a job's details, Deepgram transcribes live and GPT-4o-mini extracts structured fields into the same create-job form, and "View job file" showing a job's real technician-logged activity from `field_events`), invoices & approvals (Sections 7/2 — **view-only**: real invoice/estimate data, the contractor's one write action is approving/rejecting a customer-signed estimate or change order, never creating/editing/sending one — that's the technician mobile app's job; see HANDOFF.md §23 for a real correction where this was first built backwards), a contractor-side Knowledge Base submission panel (Section 11 — submit a fact for staff review, mirrors the KB review workflow below), fleet management (Section 4 — add/edit/retire vehicles, an honest "no telemetry connected" health status since no OBD-II integration exists), and the customer database (Section 5 — add/edit, real job counts and lifetime value) are real; the rest (reports & analytics, data export, team/RBAC, retention) is intentionally still mock data (inline mock state in `ContractorCommandDashboard.jsx` — `src/command-dashboard/dashboardData.js` now only holds a technician-roster fallback, its dead `jobs`/`fleet`/`customers` exports were removed once nothing referenced them) — a deliberate, not-yet-done scope boundary, actively being closed feature by feature.
3. **Mobile app (technician-facing)** — not in this repo. Native Flutter (confirmed decision — supersedes the FlutterFlow/React Native options floated in the planning docs). Its backend is this same Supabase/AWS stack: technician accounts already exist and authenticate via `phone + password` (and `email + password`, when an email is on file) Supabase Auth (built in this repo — see `backend/functions/add-technician/`). **See `HANDOFF.md` §11** before onboarding a developer onto that build — it consolidates the four FieldLoop AI planning docs plus the real, verified schema/auth details they need, and flags where those docs genuinely disagree with each other on scope. **`NEW_MOBILE_TEAM_HANDOFF.md`** (repo root) is the standalone, self-contained snapshot meant to be handed directly to that developer's own Claude Code session.
4. **FieldLoop AI Knowledge Base** — real, live, deployed: a fact-based Q&A retrieval system (hybrid full-text + vector search, confidence-gated LLM escalation, reachable by both the contractor dashboard and technician logins) at `POST /kb/search` / `POST /kb/trades`. `kb_entries` is physically partitioned by trade in Postgres (structural, not just a trusted filter — the client's explicit request once multi-trade content collision risk was raised). Real client-supplied content (500 facts, concrete & pavers) is imported and approved; the other 3 launch trades exist structurally with no content yet. **Contractors can also submit their own facts** (`POST /kb/submit`, Contractor Command Dashboard Section 11) — lands as `pending`, reviewed either via the Platform Overview's review queue (real approve/reject buttons, §24) or, for the original bulk-CSV import specifically, `backend/scripts/approve-kb-entries.mjs`/`reject-kb-entries.mjs`. Full build/decision history in `HANDOFF.md` §22–§24 and `Fieldloop Docs\FieldLoop_KB_Technical_Design.md` (a sibling folder to this repo, shared with the client) — an earlier pilot version of this feature (`estimate_knowledge_base`, `KnowledgeBasePanel.jsx`) was built first, then deliberately retired in favor of this real system; see §22 for why.
5. **Platform Overview** (`/staff/platform`, `admin` role only) — a cross-contractor view for FieldLoop staff (the client and the Jenex dev team), not scoped to one tenant. Real 5-tab structure (Overview / Contractors / Usage / Revenue / Knowledge Base — a sortable, clickable contractor roster, not a static list) plus a per-contractor drill-down page (`/staff/platform/contractors/:id`) showing that contractor's real profile, compliance, financials, technicians, jobs, invoices, and KB submissions. Revenue is honestly `$0` today — no real invoicing exists yet, that's the mobile app's build. See `HANDOFF.md` §24–§25.

**Read `HANDOFF.md` before making non-trivial changes.** It's the living doc: full schema (including `CHECK` constraints and recurring bug patterns to watch for), the Lambda→route map, AWS resource names, security model, and a running log of what's been tested and what hasn't. This file is intentionally short — `HANDOFF.md` has the depth.

## Stack

React 19 + Vite (frontend) → API Gateway HTTP API → AWS Lambda (Node 20.x) → Supabase Postgres (service-role key) + AWS Secrets Manager (encrypted fields: EIN, SSN, DOB, bank details, Stripe keys — never stored in plaintext or sent to the browser).

**External vendors, live and billable**: Deepgram (speech-to-text) and OpenAI/GPT-4o-mini (structured extraction) power voice-to-job-schedule (HANDOFF.md §17) — both real, working, paid APIs as of this writing, keys in `fieldloop/deepgram-credentials` / `fieldloop/openai-api-key`. **Google Maps Geocoding API** (§21.1) geocodes a job's service address on creation — real, working, paid, key in `fieldloop/geocoding-api-key` (the user's own key). Twilio (SMS) and SES (email), used for technician credential delivery (§10), are scaffolded but **not yet live** — no secret populated, calls no-op gracefully.

## Commands

```powershell
npm run dev              # Vite dev server, http://localhost:5173
npm run build             # production build
npm run lint              # oxlint
```

**Deploying a Lambda change** (from `backend/functions/`):
```powershell
.\package-lambda.ps1 -FunctionName <name>
aws lambda update-function-code --function-name fieldloop-<name> --zip-file fileb://<name>/function.zip
```
`backend/functions/shared/` is the master copy of shared helpers (`auth.js`, `contractorAuth.js`, `technicianAuth.js`, `supabaseClient.js`, `secrets.js`, `ipAllowlist.js`, `contractorDraft.js`, `messagingAdapter.js`, `technicianSetupTokens.js`, `geocoding.js`) — after editing one, copy it into every function folder's own `shared/` before packaging (no Lambda Layer is set up).

**Browser-driven testing**: Playwright is a real `devDependency`. Fresh checkout needs `npx playwright install chromium` once. No project skill exists yet for driving this app — worth generating one via `/run-skill-generator` if this becomes routine.

## Known gotchas (see `HANDOFF.md` for full detail)

- **Dev server must run on port 5173.** API Gateway's CORS `AllowOrigins` is hardcoded to `http://localhost:5173` — if a stale `npm run dev` from an earlier session is squatting on that port, Vite silently picks 5174+/5177 and every Lambda call fails client-side with an opaque `Failed to fetch`. Check `netstat -ano | grep 517` for stale `node.exe` processes if this happens.
- **Schema columns that look like status enums are sometimes real `timestamptz` columns**, and several text columns have `CHECK` constraints requiring specific lowercase/snake_case values that don't match older mock-UI display text. Before wiring a new `<select>` to a DB column, check for a constraint first: `select conname, pg_get_constraintdef(oid) from pg_constraint where contype='c' and conrelid::regclass::text = '<table>';`
- **`revealedValues` in `RegistrationDashboard.jsx` is keyed by stable column name** (e.g. `'dob_ref'`), never by the field's current `*_ref` value — the latter is `undefined` for brand-new contractors and would collide every unset field onto the same key.
- Never forward masked display placeholders (e.g. `"••••••••1212"`) to a save call as if real — only send a plaintext value when the user actually revealed/edited it.
- **Deepgram's short-lived streaming JWT authenticates via `Sec-WebSocket-Protocol: ['bearer', jwt]`**, not a query parameter and not the `['token', apiKey]` trick used for static API keys — a plausible-looking third-party example led to a wrong first implementation here (see HANDOFF.md §17 for the full story and why it's worth verifying vendor auth mechanisms empirically rather than trusting secondary sources).

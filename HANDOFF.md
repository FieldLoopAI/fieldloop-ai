## 1. What this app actually is

Two separate products live in one repo:

1. **Registration Dashboard** (`/staff/login`, `/staff`) — an internal tool for FieldLoop **staff** (roles: `admin`, `onboarding`, `finance`, `support`, `jenex_dev`) to onboard and manage contractor records through an 8-step wizard. **This is what the recent work focused on.** Fully wired to real data.
2. **Contractor Command Dashboard** (`/`, `/dashboard`) — the contractor-facing product (dispatch, technicians, fleet, customers, invoicing, reports, data export, team management). **Only the login/identity is real** — everything else still renders static mock data from `src/command-dashboard/dashboardData.js`. This was a deliberate scope decision (see §7).

## 2. Architecture

```
React (Vite)  →  API Gateway (HTTP API)  →  Lambda (Node 20.x)  →  ┬→ Supabase Postgres (service-role key)
                                                                     └→ AWS Secrets Manager (encrypted fields)
```

**Why not call Supabase directly from the browser for the registration dashboard?**
1. Sensitive fields (EIN, SSN, DOB, home address, bank routing/account, Stripe keys, backup card) must never be stored as plaintext in Postgres or touch the browser — they're written to AWS Secrets Manager, with only a `*_ref` pointer string stored in the DB. A browser can't safely hold AWS credentials to do that.
2. Row Level Security in this project is **table/row-level, not column-level** — the `"fl staff read"` RLS policies grant *any* authenticated staff member full SELECT on every column of `contractors`/`contractor_principals`/etc. The per-role field masking (e.g. `support` shouldn't see PII/compliance/financials at all, `finance` shouldn't see stripe keys) has to happen somewhere trusted — that's the `get-contractor` Lambda, not the client.

The **Contractor Command Dashboard** (once/if it's wired for real) is a different story — its tables (`customers`, `jobs`, `technicians`, `vehicles`, etc.) already have proper tenant-isolation RLS (`contractor_id = get_my_contractor_id()`), so direct browser→Supabase reads would actually be fine there. That's future work, not done yet.

## 3. Real Supabase schema (as confirmed with the user, not assumed)

Tables: `contractors`, `contractor_principals`, `contractor_contacts`, `contractor_compliance`, `contractor_operations`, `contractor_financials`, `contractor_system_meta`, `access_audit_log`, `fl_users`, `contractor_users`, `system_settings` (new — see §5), plus a full (currently unused by real code) product schema: `customers`, `technicians`, `vehicles`, `jobs`, `job_technician_assignments`, `field_events`, `estimates_and_change_orders`, `invoices`, `data_export_requests`.

Key points:
- `fl_users` and `contractor_users` both have a legacy `password_hash` column (unused now) and a nullable `auth_user_id` column that links to Supabase's own `auth.users` table. **A row in `fl_users`/`contractor_users` with no `auth_user_id` set cannot log in for real**, even if a Supabase Auth account with the same email exists — the two have to be explicitly linked (see §8).
- `fl_users.ip_allowlist` is `inet[]` — already existed, used by the IP-allowlist enforcement (§6).
- Postgres helper functions `get_my_fl_role()` and `get_my_contractor_id()` already exist and back most RLS policies.
- Some fields that existed in the original mock/UI **have no real column** and were removed from the step components: `contractor_operations.business_segment/saturday_hours/subcontractor_info` (folded `saturday_hours` into `business_hours` jsonb `{weekday, saturday}` instead), `contractor_compliance.gl_effective_date/gl_agent_name/gl_agent_phone`, `contractor_system_meta.payment_health/dispute_count/suspension_flags`, `contractor_contacts.use_when`, `contractors.google_business_url`. If you're wondering why a field from an old screenshot/spec isn't in the UI anymore, this is why — it was never real.
- `contractors.is_sandbox` did **not** exist in the original schema dump and was added via migration (§5) because the Jenex Developer role restriction depends on it.
- **Recurring bug pattern, watch for it**: several columns that look like a status enum in the original mock UI (`"Verified"`/`"Pending"`/`"Failed"` style dropdowns) are actually real `timestamptz` columns in the schema (`contractor_compliance.gl_coi_uploaded_ts`, `contractor_principals.sanctions_check_ts`, `contractor_financials.micro_deposit_verified_ts`). Sending the literal option text (e.g. `"Pending"`) crashes with `invalid input syntax for type timestamp with time zone`. The fix pattern used everywhere this came up: collapse the dropdown to a binary state (has a real timestamp vs. `null`), setting `new Date().toISOString()` on the "positive" transition and preserving the existing timestamp rather than overwriting it if already set. If you add a new field bound to a `*_ts` column, check whether it's genuinely a timestamp before wiring it to a multi-option `<select>`.
- **Second recurring pattern**: several text columns have Postgres `CHECK` constraints restricting them to specific lowercase/snake_case values that don't match the original mock UI's display-text values. Confirmed via `select conname, pg_get_constraintdef(oid) from pg_constraint where contype='c' and conrelid::regclass::text in (...)` against all 7 registration tables — the full list, in case another mismatch surfaces:
  - `contractors.business_structure` → `llc`/`s_corp`/`c_corp`/`sole_prop`/`partnership` (already matched, no fix needed)
  - `contractor_principals.id_verification_status` → `pending`/`verified`/`failed` (was 4 unrelated display strings — fixed, `Step3OwnershipPrincipal.jsx`)
  - `contractor_contacts.contact_type` → `primary`/`secondary`/`billing`/`field_ops`/`emergency` (already matched)
  - `contractor_contacts.preferred_channel` → `voice`/`sms`/`email` (was a **free-text input** that could send anything — fixed to a `<select>`, `Step4KeyContacts.jsx`)
  - `contractor_financials.account_type` → `business_checking`/`business_savings` (was `"Business Checking"`/`"Business Savings"` — fixed, `Step7SecureFinancials.jsx`)
  - `contractor_system_meta.status` → `pending`/`active`/`suspended`/`terminated` (the `"Pending activation"` default was wrong on both ends — fixed in `Step8InternalSystemSettings.jsx` **and** in `create-contractor`'s seed insert, see below)
  - `contractor_system_meta.risk_score` → integer 0–100 (was a **free-text field showing `"Low (12/100)"` demo text**, would have sent `NaN` on save — fixed to a numeric input, `Step8InternalSystemSettings.jsx`)
  - If you add a new dropdown/select bound to a real column, check for a `CHECK` constraint on it first with the query above rather than guessing at values.
- **Real bug found this way**: `create-contractor/index.js` seeded `contractor_system_meta.status` as `'Pending activation'`, which violates the check constraint above — **and the insert's error wasn't being checked**, so every new contractor's system-meta row may have silently failed to get created (contractor row exists, but no meta row, breaking Step 8 and later activation). Fixed to `'pending'` plus an actual error check. **This Lambda needs redeploying** (`package-lambda.ps1 -FunctionName create-contractor` → `aws lambda update-function-code --function-name fieldloop-create-contractor ...`) — any contractor created before this fix may be missing its `contractor_system_meta` row; check with `select c.id, c.legal_name from contractors c left join contractor_system_meta m on m.contractor_id = c.id where m.contractor_id is null;` and backfill manually if needed (`insert into contractor_system_meta (contractor_id, status) values ('<id>', 'pending');`).
- **Unverified, worth checking if it comes up**: `physical_state`/`mailing_state`/`license_state` are `character` (`bpchar`) columns — the UI sends full state names like `"Florida"`. If the column's declared length is short (e.g. `char(2)` for a state code), this would either truncate silently or error depending on Postgres's assignment-cast behavior. Hasn't errored in testing yet, but if it does, check the actual length with `select character_maximum_length from information_schema.columns where table_name='contractors' and column_name='physical_state';`.

## 4. Frontend structure

```
src/
  App.jsx                              — react-router-dom routes (see below)
  main.jsx                             — wraps App in <BrowserRouter>
  shared/services/
    supabaseClient.js                  — browser Supabase client, ANON key only, Auth use only
    api.js                             — fetch wrapper for all Lambda calls (attaches JWT bearer token)
    mockDb.js                          — legacy mock DB; now only used by ContractorCommandDashboard's
                                          non-identity mock panels (jobs/fleet/customers/etc.)
  registration-dashboard/
    RegistrationDashboard.jsx          — the 8-step staff wizard, now backed by api.js
    StaffLoginPage.jsx                 — real Supabase Auth login for staff
    useStaffAuth.js                    — session + fl_users role lookup hook
    steps/Step1..Step8*.jsx            — one component per wizard step
  command-dashboard/
    ContractorLoginPage.jsx            — real Supabase Auth login for contractors
    useContractorAuth.js               — session + contractor_users lookup hook
    ContractorCommandDashboard.jsx     — receives real `tenant` as a prop; rest of UI still mock
    dashboardData.js                   — mock jobs/technicians/fleet/customers (tenant removed from here)
```

**Routes** (`src/App.jsx`):
| Path | Component | Auth |
|---|---|---|
| `/` , `/dashboard` | Contractor login → `ContractorCommandDashboard` | `contractor_users` via Supabase Auth |
| `/staff/login` | `StaffLoginPage` | — |
| `/staff` | `RegistrationDashboard` | `fl_users` via Supabase Auth, redirects to `/staff/login` if not signed in |

**`src/shared/services/api.js`** is the single place that knows how to call every Lambda. Every function:
1. Pulls the current Supabase session's JWT (`supabase.auth.getSession()`).
2. Sends it as `Authorization: Bearer <token>`.
3. **Critical rule, don't break this**: for any secret-backed field (EIN, DOB, SSN, home address, routing/account/stripe/card), it only sends a plaintext value if the user actually revealed *and edited* it (tracked in the `revealedValues` map). It never forwards the masked display placeholder (e.g. `"••••••••1212"`) as if it were real — doing so would let a save silently overwrite a real secret with garbage. See `revealedOnly()` in `api.js`.

**Shared helpers** (`backend/functions/shared/`):
- `auth.js` — `requireRole(event, allowedRoles)`: validates the JWT, looks up the caller's `fl_users` row, returns `{ id, role, email }`, throws if role isn't allowed. Used by the **staff**-side Lambdas above.
- `contractorAuth.js` — `requireContractorRole(event, allowedRoles)`: the contractor-side equivalent, looks up `contractor_users` instead, returns `{ id, contractor_id, role, email }`. Used by every Lambda in the Contractor Command Dashboard table above.
- `supabaseClient.js` — `getSupabaseClient()`: fetches the Supabase **service-role** key from Secrets Manager (`fieldloop/supabase-service-credentials`), returns a cached client. **Passes `{ realtime: { transport: WebSocket } }` using the `ws` npm package** — this is required because `@supabase/supabase-js`'s `createClient()` initializes a Realtime client by default, which throws on Lambda's `nodejs20.x` runtime (no native WebSocket until Node 22) unless a WebSocket implementation is explicitly given. If you ever see `"Node.js detected but native WebSocket not found"`, this is why — make sure `ws` is in the function's `package.json` and this fix hasn't been dropped from a `shared/supabaseClient.js` copy.
- `secrets.js` — `getSecret`/`storeSecret`/`deleteSecret` against AWS Secrets Manager. `deleteSecret` uses a **standard delete** (default recovery window), not force-delete-without-recovery — this runs against real production secrets, so it keeps AWS's built-in recovery window as a safety net; §20.
- `ipAllowlist.js` — `enforceIpAllowlist(event, flUser)`: for `admin`/`finance` roles, checks the caller's source IP against `fl_users.ip_allowlist`, but only when `system_settings.ip_allowlist_enabled` is true. Staff-side only.
- `contractorDraft.js` — the actual save logic (upserts across `contractors`/`contractor_principals`/`contractor_contacts`/`contractor_compliance`/`contractor_operations`/`contractor_system_meta`), shared by `save-contractor-draft` and `activate-contractor` (activation always saves the draft first).
- `messagingAdapter.js` — §19. `sendMessage(supabase, { preferredChannel, phone, email, smsBody, emailSubject, emailHtml })`, routes through `dev_log`/`dev_email`/`prod_sms` per the `MESSAGING_PROVIDER` env var. Used by `add-technician`/`update-technician`/`resend-technician-setup`.

## 6. Security model, concretely

- **Role → field visibility matrix** (ported from the original mock, now enforced server-side in `get-contractor`/`reveal-field`, not just in the UI):
  - `support`: contact info only; PII/compliance license numbers/financials refs nulled or masked.
  - `finance`: full business info; no PII; bank/routing visible (last-4 in the UI, full value if revealed — there's no partial-reveal capability, see below); no Stripe.
  - `onboarding`: full read/write except financials (admin-only) and no Stripe reveal.
  - `admin`: full access to everything, admin-only for financials writes, PDF export, system settings writes.
  - `jenex_dev`: blocked entirely from non-sandbox (`is_sandbox = false`) contractor records.
- **Important nuance**: `reveal-field` either returns the full decrypted secret or throws — there's no "partial reveal." So "last 4 only" roles in the UI table are really "sees a cosmetic masked placeholder until they click reveal, then get the full value, same as admin" — the actual security boundary is *whether the `*_ref` is nulled out at all* (controls whether the reveal button even appears/works), not a partial-value distinction.
- **`save-contractor-financials` and the principal-PII path in `save-contractor-draft`** only call `storeSecret()` (re-encrypt) when the frontend actually sent a new plaintext value for that specific field. If omitted, the existing `*_ref` is preserved untouched. This was a real bug in the original code (unconditional `storeSecret` calls) that would have silently corrupted a secret the first time a save happened without that field being revealed.
- **IP allowlist and session/password policy** are real now (`system_settings` table + `ipAllowlist.js`), not just UI simulation like in the old mock.
- **`revealedValues` (frontend, in `RegistrationDashboard.jsx`) is keyed by stable column name** (`'dob_ref'`, `'ssn_last4_ref'`, `'home_address_ref'`, `'ein_ref'`, `'routing_number_ref'`, `'account_number_ref'`, `'stripe_account_id_ref'`, `'backup_card_ref'`) — **not** by the field's current `*_ref` *value*. This matters: a brand-new contractor's `contractor_principals`/`contractor_financials` rows don't exist until the first save, so every one of those ref values is `undefined` — keying by value would collide every unset field onto the same `"undefined"` object key, and (worse) permanently lock the input `readOnly` since the "REVEAL" button only ever renders when a ref exists. Each masked field in `Step2BusinessIdentity`/`Step3OwnershipPrincipal`/`Step7SecureFinancials` computes `const hasRef = Boolean(p.some_ref); const editable = !hasRef || revealedValues['some_ref'] !== undefined;` — when there's no ref yet, the field is just freely editable from the start (no reveal button shown), which is what makes registering a *brand-new* contractor's Step 3/Step 7 fields actually possible. If you ever see two different secret fields' values overwriting each other, or a field on a new record permanently stuck blank/read-only, this is the mechanism to check first. `api.js`'s `revealedOnly()` takes a **static** column-name → Lambda-field-name map (`PRINCIPAL_SECRET_FIELDS`, `FINANCIALS_SECRET_FIELDS`) for the same reason.

## 7. Deliberate scope boundaries (don't be surprised these aren't done)

- **Contractor Command Dashboard's operational panels — partially real as of §23.** Dispatch (§12), technicians (§10/§16), invoices (§23, read-only), approvals/estimates (§23, read + approve/reject only), Job File (§23), and Knowledge Base submission (§23) are real. **Still 100% mock data**: fleet, customers, reports & analytics, data export, team/RBAC, retention queue (`dashboardData.js` for fleet/customers; inline mock state in `ContractorCommandDashboard.jsx` for the rest). The underlying Supabase schema for all of this already exists with proper tenant-isolation RLS — wiring the remainder up is future work, not because it's hard, but because it hasn't been scoped/prioritized yet.
- **The registration dashboard landing is now a two-tab affair**, not a single cluttered screen: a `mode` state (`'new' | 'existing'`) in `RegistrationDashboard.jsx` controls which panel shows when no contractor is loaded, defaulting to `'new'` for roles that can create (`admin`/`onboarding`) or `'existing'` otherwise.
  - **"New Registration" tab**: Legal Business Name + EIN → calls `api.createContractor`/the `create-contractor` Lambda, then loads the new record straight into Step 2 to keep filling it out.
  - **"Existing Contractors" tab**: a debounced (~300ms) search-by-name box backed by the new `list-contractors` Lambda, rendering clickable results (name + public ID + a SANDBOX badge where relevant); a manual "paste a Contractor ID directly" fallback sits below it for power users/debugging. Loading (from search or manual paste) is now an explicit action (`loadContractor(id)`), not fired on every keystroke like the very first version was.
  - Once a record is loaded, a "← Back to search" link in the `contractor-header-area` block (`handleBackToSearch`) resets back to the tab picker without a page refresh.
  - **Navigation state survives a tab reload**: `mode`/`activeContractorId`/`activeStep` are mirrored to `sessionStorage` (key `fieldloop_staff_nav`) and restored on mount (re-fetching the contractor fresh from `get-contractor`, never trusting stale client data). This exists because Chrome/Edge's "memory saver" / sleeping-tabs feature fully unloads a backgrounded tab and reloads it on refocus, which otherwise wipes all in-memory React state and looks like the app "forgot where you were." Deliberately **not** persisted: `revealedValues` (decrypted secrets), `credentialsData` (passwords), or the full `contractorData` object — only which record/step/tab, nothing sensitive, and it's cleared on sign-out so the next login on the same tab doesn't inherit the previous person's loaded contractor.
- There's a project doc at `Fieldloop Docs\FieldLoop_AI_Lambda_Supabase_Integration_Guide.docx` that describes a **different** intended architecture (one Lambda per wizard step, direct browser→Supabase reads for the registration dashboard). We deliberately diverged from it: direct reads would only be table/row-level secured, not column-level, which would let e.g. `support` accounts receive full rows (including PII/financial `*_ref` values) over the wire even if the UI chose not to render them. The consolidated `get-contractor`/`save-contractor-draft` approach was kept for real security instead of doc-consistency — this was an explicit decision, not an oversight.

## 10. Add Technician Feature (Command Dashboard — Section 3)

### Overview
Replaces the static mock data in Section 3 (Technicians) of the Contractor Command Dashboard with an end-to-end implementation for creating and roster-managing technician accounts. **Originally implemented by another agent (Antigravity) in a prior session; independently code-reviewed and empirically verified (not just read) in this session, which found the deployed feature was completely non-functional plus a serious access-control gap — both fixed here.** See the **"Round 5 — review & fix"** entry below for the full audit trail; the architecture described in this section is the corrected, currently-deployed version.

### Architecture & Security Flow
1. **Contractor Admin Form**: Only `owner_admin` contractor users see/can use the "Add technician" action (gated client-side by `tenant.role`, enforced server-side regardless). They fill in Full Name, Mobile Phone (required — this is the technician's login), Email (optional, required only if Email is the chosen delivery channel), Role/Specialty, Certifications, Hourly Rate, Billable Rate, and a **Credential Delivery Channel** (`sms` or `email`).
2. **Backend Authentication (`requireContractorRole`)**: Calls are authenticated using the contractor user's Supabase JWT and checked against the `contractor_users` table, role must be `owner_admin`.
3. **Credential Auto-Generation**: Cryptographically secure 16-character password generated in-memory using Node `crypto.randomInt` CSPRNG (combining uppercase, lowercase, digits, and special characters). Never stored or logged in plaintext.
4. **Supabase Auth User — phone identity, not email**: Created via `supabase.auth.admin.createUser({ phone, password, phone_confirm: true, user_metadata: { must_change_password: true, contractor_id } })`. ## 11. Mobile App (Technician-Facing) — Context for Whoever Builds It

**This section exists so a developer picking up the native Flutter mobile app build doesn't have to re-read four planning documents to get oriented.** It's distilled from `Fieldloop Docs\FieldLoop_AI_Prototype_6-Week_Roadmap_v1.1.docx`, `FieldLoop_Pre-Implementation_Review.docx`, `FieldLoop_AI_Master_Implementation_Guide_v2.docx`, and `FieldLoop_AI_Contractor_Walkthrough_CONFIDENTIAL.pdf` — none of which live in this repo (they're in `Fieldloop Docs\` alongside it). Those four documents **disagree with each other** on real scope questions (§11.5 below) — this section flags every disagreement explicitly rather than silently picking a side, because guessing wrong here wastes build time exactly the way guessing at an unverified `CHECK` constraint has elsewhere in this project (§3).

### 11.1 What FieldLoop AI actually is (the full product vision)

A voice-first, ambient-capture field service platform for residential/light-commercial trade contractors (HVAC, general contracting). The pitch against ServiceTitan/Jobber/Housecall Pro: those charge $65–400+/user/month; FieldLoop is transaction-fee-only, no subscription. **System boundary** (explicitly confirmed by the partner, not up for debate): FieldLoop's responsibility starts the moment a job record is created and ends when the platform fee is collected and the retention sequence completes. It does not do lead generation, marketing, or scheduling logic — those stay the contractor's own systems. Confirmed beta testers: **Luxe Renovation** (Phase 1 alpha — this is the "Playwright Full Run..." style test contractor already in this repo's Supabase; general contractor, concrete/roofing/renovation), **H&M Contractors, LA** (Phase 2 beta, same trade profile, sees the polished version).

### 11.2 The interaction model — wake word + direction word

Every voice command follows the same shape: the wake word **"FieldLoop"** activates listening (like "Alexa"), followed immediately by a **direction word** that carries the intent — `"FieldLoop, Photos"`, `"FieldLoop, Prepare Estimate"`, `"FieldLoop, Change Order"`, `"FieldLoop, Job Complete"`, etc. Every voice command has a **bilingual (English/Spanish) equivalent** and, critically, **a visible on-screen button as a silent failsafe behind every single voice action** — jobsites are loud and phones mishear; voice is the fast path, never the only path. Full bilingual command table is in the Contractor Walkthrough doc if the exact word list is needed (photo capture, troubleshooting, estimate build/edit/send, change order, scan part, job complete, generate invoice, process payment, log delay, route to manager).

### 11.3 The shared 8-beat job spine

Every job — a 45-minute repair or a 3-week build — moves through the same sequence; scenarios just stretch or compress each beat:

| Beat | What happens | Driven by |
|---|---|---|
| 1. Intake | Job created: address, contact, problem, parts hint, appointment | Contractor's dispatcher |
| 2. Assign & notify | Job pushed to a specific technician's phone as their Active Job | Dispatcher → app |
| 3. En route | Tech taps En Route; navigation launches; job data cached offline | Technician + app |
| 4. Arrival | Geofence (or manual "I've Arrived" failsafe) starts the labor clock | GPS + failsafe toggle |
| 5. Assess | Photos + spoken notes archived; troubleshooting/coaching on demand | Technician voice + AI |
| 6. Estimate | Proposal built by voice, reviewed, sent, signed | Technician voice + customer |
| 7. Execute & invoice | Work done; change orders; usage logged; invoice compiled; payment taken | Technician + Stripe Connect |
| 8. Retain | Automated follow-up sequence (24hr/48hr/3mo/12mo) | Backend, no human touch |

A **`Project` vs `Service Call`** flag set at intake changes downstream behavior significantly: a Project expects multi-day labor tracking, phased/dimensional estimating, and **milestone-based progress billing** (e.g. 30% deposit on signed proposal — and the job doesn't hit the dispatch board as scheduled until that deposit clears — then 30%/25%/15% at defined phase-complete voice triggers) instead of one estimate-to-invoice pass.

## 12. Job Dispatch Feature (Command Dashboard — Section 1)

### Overview
Replaces the static mock data in Section 1 ("Live dispatch board") of the Contractor Command Dashboard with a real, end-to-end implementation covering Beats 1–2 of the 8-beat job spine (§11.3): job intake and technician assignment. Deliberately scoped to a **structured form**, not the chat/voice-to-structured-fields flow described in the planning docs — that's an explicit, confirmed-with-the-user follow-up once the voice/AI vendor question (§11.5) is resolved, not part of this build.

### Architecture
Follows the exact pattern established by the Add Technician feature (§10): three Lambdas, `owner_admin`-only (the only role that can currently exist per `contractor_users_role_check`), service-role Supabase client, `requireContractorRole` for auth.

- **`list-jobs`** (`POST /jobs/list`) — returns `{ jobs, customers }` in one round trip (customers power the create-job modal's picker, avoiding a 4th Lambda). Jobs are joined to `customers`/`technicians` via PostgREST FK embeds, always include unscheduled (`draft`) rows regardless of the date filter, and are annotated with `has_conflict`/`conflict_with` by an in-memory pass over same-technician overlapping time windows — **conflict detection lives entirely in this read path**, not duplicated into the write Lambdas, so it's always correct and a badge survives a page reload instead of being a one-shot toast.
- **`create-job`** (`POST /jobs`) — accepts either an existing `customer_id` or inline `new_customer` fields (deduped by normalized phone before insert, so re-entering the same customer's number reuses their row instead of creating a duplicate). `status` is `'scheduled'` only if both a technician and a start time are given at creation, otherwise `'draft'`. Rolls back a just-created customer if the job insert then fails.
- **`assign-job`** (`POST /jobs/assign`) — reassigns/assigns a technician on an existing job. Refuses to touch a job whose status has moved past `draft`/`scheduled` (i.e. `en_route` through `paid` — those beats belong to the not-yet-built mobile app; a dispatcher silently reassigning a job that's already on-site would be a real data-integrity problem). No unique constraint exists on `job_technician_assignments` to `.upsert()` against, so this deletes-then-inserts the assignment row.

**Every client-supplied foreign key (`customer_id`, `technician_id`, `job_id`) is re-verified as belonging to the caller's own `contractor_id` before use** — these Lambdas use the service-role key, which bypasses RLS entirely (§2), so a hand-crafted request could otherwise attach or mutate another contractor's records. Verified live: crafted requests with another contractor's real `customer_id`/`technician_id`/`job_id` all correctly return 400, not silent success.

### Real CHECK constraint values — verified live via probe-insert/delete, not guessed
- **`jobs.status`**: `draft`, `scheduled`, `en_route`, `on_site`, `complete`, `closed`, `invoiced`, `paid`. (Rejected: `unassigned`, `assigned`, `in_progress`, `change_order_pending`, `completed`, `cancelled`/`canceled`.)
- **`jobs.job_type`**: **only `'service_call'` is currently valid** — every other plausible candidate (`project`, `installation`, `repair`, `maintenance`, `Service Call`, `Project`, `new_construction`, etc., ~20 values tested) was rejected. This means the "Project vs. Service Call" flag described throughout the planning docs (§11.3, milestone billing, phased estimating) **has no schema support yet** — that's a real gap, not an oversight in this feature; a future migration would need to extend this constraint before a Project-mode job could ever be created.

## 13. Fixed: Contractor Command Dashboard "reloads and loses everything" on tab/app switch

### Root cause
**Not an app bug in the sense of broken code — the browser (or OS, on mobile) was genuinely destroying and reloading the tab**, not just repainting it. Confirmed by grepping the entire frontend for `window.location`, `location.reload`, `location.href`, `visibilitychange`, `beforeunload`, and any service-worker/PWA config — none exist anywhere in this app. This is Chrome/Edge's "Memory Saver" (or the equivalent on a mobile browser/OS) reclaiming memory from a backgrounded tab: when you switch away and come back, the JS execution context is gone and the browser does a real network reload, which is indistinguishable from the user hitting F5. No in-page lifecycle listener (there's no Page Visibility API equivalent of "please don't discard me") can prevent this — it happens *to* the page from outside, not something the page's own code triggers or can intercept.

This exact mechanism was already diagnosed once before, on the login pages (§9 Round 4) — this report is the same root cause resurfacing on the dashboard itself, now with a real fix instead of a browser-setting workaround, since it kept recurring.

### Fix
Extended the `sessionStorage`-based state-recovery pattern already used in `RegistrationDashboard.jsx` (§7) to `ContractorCommandDashboard.jsx` — sessionStorage is the right tool specifically because it *survives* a tab reload within the same tab (unlike in-memory React state), so even though the reload itself can't be prevented, the app can restore itself close to where the user was immediately after.

- **Navigation position** (`activePage` — which of the 10 dashboard sections is active) is mirrored to `sessionStorage` (`fieldloop_contractor_nav`) on every change and read back on mount.
- **In-progress form data** for the two write modals (`AddTechnicianModal`, `CreateJobModal`) is mirrored to `sessionStorage` (`fieldloop_add_tech_draft` / `fieldloop_create_job_draft`) on every keystroke, and the modal **reopens itself automatically** on mount if a draft exists — the parent checks `Boolean(sessionStorage.getItem(...))` for its initial `showXModal` state, and the modal restores its own `formData` from the same key. Unlike the registration wizard's justified exclusion of secrets (SSN, bank details, passwords — see §7), neither of these two forms collects anything sensitive while being filled out (the technician's password is generated server-side and shown only *after* submission, and that display-only value is never written to storage), so the full field-by-field draft is safe to persist.
- **Drafts are cleared**, not left to linger, in three cases: (1) successful submission — the data's now saved for real; (2) explicit close (Cancel, the ✕ button, or clicking the backdrop) — a deliberate "never mind" shouldn't resurrect old input the next time the modal opens; (3) sign-out — via a `clearAllPersistedDashboardState()` call wrapped around the Logout button's `onClick`, so the next person to sign in on the same tab never inherits a stranger's half-typed technician or job.

### Found and fixed along the way
A real (if narrow-window) bug surfaced while testing this: right after a reload, `displayTechs` briefly falls back to the mock technician array (`realTechs` starts `null` until `loadTechs()` resolves) — and mock technicians have no `id` field at all (`dashboardData.js`'s `technicians` array only has `name`/`specialty`/`phone`/etc.). The dispatch board's reassign `<select>` (added in §12) mapped those options with `key={t.id}`, so for that brief window every option shared the same `undefined` key, throwing a real React "missing key" warning — reproduced deterministically via Playwright (not flaky) once isolated by testing each step individually. The *existing* technician roster table already guarded against this exact case (`key={t.id || t.name}`); the new reassign dropdown just hadn't matched that precedent. Fixed identically in both the dispatch-board reassign select and `CreateJobModal`'s technician select (`key={t.id || t.name}`, `value={t.id || ''}`).

Also note for future debugging: **a stale Vite dev-server / HMR module cache can itself produce a phantom version of this same "missing key" warning** that references code that no longer matches the actual source (confirmed by direct source inspection finding correct keys everywhere the warning pointed to) — after enough hot-reloads to one file in a single long dev session, if a console warning looks like it can't possibly be right, restart the dev server with `node_modules/.vite` cleared before assuming it's a real bug.

### Files
`src/command-dashboard/ContractorCommandDashboard.jsx` only — no backend changes.

### What was tested (real, live — via `page.reload()`, which is a faithful proxy for a tab discard: same destroyed JS context, same `sessionStorage` survival, same fresh network fetch)
1. Navigated to Section 3 (Technicians), reloaded the page → confirmed it lands back on Section 3, not the default Section 1.
2. Opened Add Technician, typed into `full_name` and `role`, reloaded the page → confirmed the modal reopened automatically with both values intact.
3. Clicked Cancel, reopened Add Technician → confirmed the form was blank (the draft doesn't persist forever after an explicit close).
4. Filled the Create Job modal's new-customer name, confirmed a draft existed in `sessionStorage`, triggered Logout, signed back in → confirmed the modal did *not* auto-reopen (sign-out actually clears it, not just visually resets).
5. Reran the full suite on a freshly restarted dev server with the Vite cache cleared, confirming zero console errors — including re-verifying the React key-warning fix in isolation, step by step, to rule out it being timing-dependent flakiness rather than the actual fix.

### Report
User created a job with a `scheduled_start` on a different date, and it didn't appear on "Live dispatch board — today". Confirmed via a direct DB query that the job *was* stored correctly — the board's own date filter was hiding it, and there was no way to look at any day other than today (the "View calendar" button next to the board was an unwired mock button, not a real control).

### Fix
- `loadJobs(dateStr)` now takes the day to query instead of hardcoding `new Date()`; a new `selectedDate` state (defaults to today, `YYYY-MM-DD` local) drives it.
- The inert "View calendar" button is now a real `<input type="date">`, plus a "Today" quick-jump button that only appears when viewing a different day. The panel title and the first KPI card ("TODAY'S JOBS" → "JOBS THIS DAY" when not viewing today) both reflect whichever date is selected.
- Draft/unscheduled jobs (`scheduled_start IS NULL`) still always show regardless of date, unchanged from §12's original design — only *scheduled* jobs are date-filtered.
- No backend change — `list-jobs` already accepted an arbitrary `{ from, to }` range; only the frontend was hardcoding "today" into that range.

### Found and fixed along the way: a real race condition, same class as one already fixed once before
While verifying the fix, navigating to a different date sometimes silently reverted to showing "today"'s jobs. Root cause: `loadJobs` had no request-ordering guard, so if the initial "today" fetch (issued on mount) was still in flight — e.g. a Lambda cold start — when the user picked a different date, the *newer* request's response could arrive first, then the *older, slower* "today" response would land afterward and overwrite it, clobbering the correct data with stale data. This is the exact same bug class already found and fixed once in `RegistrationDashboard.jsx`'s `loadContractor` (§9 Round 2: "a slow response could still be in flight after the user navigated elsewhere... when it finally resolved, it silently overwrote whatever the user had navigated to"). Fixed identically: a `loadJobsRequestIdRef` incremented on every call, with the response only applied if it's still the most recent request. (First pass at this fix put the staleness check inside a `finally { return; }`, which `oxlint` correctly flagged as an unsafe pattern — a `return` in `finally` unconditionally overrides the try/catch's own control flow. Rewritten as a plain conditional instead of an early return.)

### Files
`src/command-dashboard/ContractorCommandDashboard.jsx`, `src/command-dashboard/dashboard.css` (`.date-nav`). No backend/Lambda changes.

## 16. Edit / Delete Technician (Command Dashboard — Section 3)

### Why
§10 built Add Technician but left the roster's "Edit"/"Deactivate" buttons as mock no-ops. Four design decisions were made explicitly with the user before writing any code (all "Recommended" options, none contested):

1. **Soft-delete, not hard-delete.** `technicians` is referenced by `jobs.lead_technician_id` and `job_technician_assignments.technician_id` — hard-deleting would either violate the FK or destroy the historical record of who actually did a completed job. A new `technicians.is_active boolean NOT NULL DEFAULT true` column was added instead (migration `007_technicians_deactivation.sql` — a dedicated column, not a repurposed `invite_status`, since that column's own CHECK values were never verified and extending someone else's enum by guessing is exactly what §3's schema discipline warns against). The UI action is labeled **"Deactivate"**, never "Delete" — honest about what it actually does.
2. **Ban, don't delete, the Supabase Auth account.** `deactivate-technician` calls `supabase.auth.admin.updateUserById(auth_user_id, { ban_duration: '876000h' })` (~100 years — Supabase's own convention for "effectively permanent, still reversible"). This keeps `auth_user_id` intact so historical `job_technician_assignments` rows stay valid, and a future reactivation feature (not built now) would just be an unban.
3. **Editing `mobile_phone` moves the Supabase Auth login in lockstep.** `mobile_phone` is the technician's actual login identity (§10/§11), not just contact info — `update-technician` detects a normalized phone change, pre-checks per-contractor uniqueness, calls `supabase.auth.admin.updateUserById(auth_user_id, { phone, phone_confirm: true })`, then attempts an SMS notification via the same graceful-no-op Twilio pattern as §10 (returns a `warning` in the response instead of blocking the update when Twilio isn't configured — it never is yet).
4. **Deactivation auto-unassigns only *active* jobs.** Any `draft`/`scheduled` job assigned to the technician gets `lead_technician_id` cleared and its `job_technician_assignments` row deleted; `complete`/`closed`/`invoiced`/`paid` jobs keep their technician reference untouched, since that's the accurate historical record.

## 17. Voice-to-Job-Schedule (Command Dashboard — Section 1)

### Why
Section 1's dispatch board only supported creating a job by typing into `CreateJobModal` (§12). This adds a mic button that lets a contractor speak the job details instead — live transcription while they talk, an LLM extracts structured fields, those fields pre-fill the *same* `CreateJobModal`, and the contractor reviews/edits/saves exactly as before. No parallel save path; voice is purely a faster way to arrive at the same form. Planned in full with the user before any code was written (plan mode, two `AskUserQuestion` rounds) — see §11.5 in this doc for the FieldLoop AI planning docs' own (unresolved) take on voice/AI vendor choice, which this feature's decisions were weighed against but not bound by, since this is a different context (web dispatcher tool, not the mobile field app's ambient/Bluetooth-headset pipeline).

**Two vendor decisions, confirmed with the user (not unilaterally picked):**
- **STT: Deepgram** streaming, not the browser's built-in Web Speech API — better accuracy, cross-browser, matches the vendor named in the planning docs for the broader voice pipeline.
- **Extraction LLM: GPT-4o, later switched to GPT-4o-mini** — GPT-4o was the original pick, on doc-precedent (named twice in the planning docs for client-facing structured-extraction tasks; Claude was the other option, lower build-risk since I know its API cold, but zero precedent in the docs). After a cost evaluation (real vendor pricing pulled live, see the "Voice pipeline vendor setup & cost evaluation" artifact) confirmed a fixed-schema extraction task like this one doesn't need gpt-4o's extra capability, the user chose to switch to **gpt-4o-mini-2024-07-18** — ~16x cheaper ($0.15/$0.60 vs $2.50/$10 per 1M in/out tokens) with no code changes beyond the model name, since Structured Outputs works identically on both. Deepgram was unaffected by this decision.

Both are brand-new paid vendors for this repo. Until real keys exist in `fieldloop/deepgram-credentials` / `fieldloop/openai-api-key`, both new Lambdas return a clean "not configured" error — same graceful-degradation shape as Twilio/SES (§10), not a new pattern.

**Failsafe principle, carried over from the mobile app's own voice design (§11.2 — "voice is the fast path, never the only path")**: the manual "Schedule new job" flow is completely untouched and always available; voice capture is strictly an alternate way to arrive at a pre-filled version of the same form.

### Deepgram JWT auth over WebSocket — the query-param approach is wrong; corrected after real testing
Pre-launch research (a GitHub discussion on Deepgram's own repo, not their primary docs) suggested passing the short-lived JWT from `POST /v1/auth/grant` as a URL query parameter — `wss://api.deepgram.com/v1/listen?...&access_token=<jwt>` — to work around the browser's inability to set a custom `Authorization` header on a WebSocket handshake. **This is wrong.** Once real credentials existed and this was actually tested against the live API, every connection attempt failed with `401 {"err_code":"INVALID_AUTH","err_msg":"Invalid credentials."}` — confirmed definitively by bypassing the browser's deliberately-opaque `WebSocket.onerror` event and connecting from Node with the `ws` package instead, which surfaces the real HTTP response Deepgram sends back (browsers only ever expose an abnormal-closure code, never the actual reason).

**The real mechanism**: JWTs authenticate via the `Sec-WebSocket-Protocol` subprotocol, same trick static API keys use, but with `bearer` instead of `token` as the first element — `new WebSocket(url, ['bearer', jwt])` — matching the `Authorization: Bearer <jwt>` scheme JWTs actually require server-side (confirmed working first via a direct `Authorization: Bearer` header from Node, which isn't available in a browser, before finding the browser-compatible subprotocol equivalent). `VoiceCaptureModal` now connects this way; the query-parameter code path is gone entirely. **Lesson**: a community discussion thread is not a primary source — this one was subtly wrong, and cost real debugging time that empirical testing against the live API resolved in minutes once credentials existed. Trust official docs first, and verify anything else against the real API rather than assuming a plausible-sounding secondary source is correct.

### Other things found only once live testing was possible
- **OpenAI's Structured Outputs `strict: true` mode requires every schema property in `required`, including nullable ones** — there's no true "optional" field; a field that can be absent must be typed `["string", "null"]` and still listed in `required`, with `additionalProperties: false` at every object level. `voice-extract`'s `EXTRACTION_SCHEMA` follows this shape for all 10 job fields plus `flagged_fields`. (Confirmed working correctly against the real API, no issue here — noted for anyone editing the schema later.)
- **The real model sometimes names a field in `flagged_fields` even when it left that field `null`** — nothing to double-check on a blank input, so `buildInitialDataFromExtraction` (frontend) now only actually flags a field if a value was genuinely filled in. Found by inspecting real GPT-4o-mini output on an ambiguous transcript, not by guessing at edge cases in code review.
- **`getUserMedia` failures aren't limited to `NotAllowedError`/`NotFoundError`.** A real headless-browser environment with no capture backend at all threw `NotSupportedError` instead, which fell through to a bare technical message ("Not supported") rather than the friendly one. `VoiceCaptureModal`'s catch block now also treats `NotSupportedError`/`NotReadableError` as the same "microphone unavailable" case.

### What was built
- **`voice-token`** (`POST /jobs/voice-token`, owner_admin) — mints the scoped Deepgram JWT described above. No DB access needed for its own logic, but still needs the full `shared/` copy (`supabaseClient.js` + `ws`) because `contractorAuth.js` itself calls Supabase to verify the JWT and look up the caller's role — easy to assume a DB-free Lambda needs a DB-free `shared/`, it doesn't, auth always does.
- **`voice-extract`** (`POST /jobs/voice-extract`, owner_admin, **`--timeout 30`** not the usual 10 — an LLM round-trip runs longer than a simple DB call, proactively avoiding the "forgot to raise the default 3s timeout" mistake this project has already hit twice) — takes `{ transcript, client_now_iso, client_timezone }`, calls GPT-4o-mini (`gpt-4o-mini-2024-07-18` — switched from `gpt-4o-2024-08-06` post-launch on cost grounds, see above) with the strict JSON schema above. System prompt instructs: fill in only what's clearly stated, **return `null` for anything not mentioned — never guess**, and separately list anything filled in but not fully confident about in `flagged_fields`. `job_type` is **not** asked of the model at all — `create-job`'s CHECK constraint only accepts `'service_call'` (§12), so the Lambda just hard-sets it; asking an LLM to pick from a one-value enum is pure guess-risk for zero benefit.
- **`VoiceCaptureModal`** (new, `ContractorCommandDashboard.jsx`) — a small modal separate from `CreateJobModal`, not crammed into the top of an already-large form. State machine: idle → connecting → listening (live interim/final transcript display, finalized text in normal weight, in-progress text gray/italic) → extracting → done (closes itself, hands data to the parent) or error (every error state — mic denied, Deepgram/token failure, empty transcript, extraction failure — has a visible "Fill In Manually Instead" button, never a dead end). Stopping sends Deepgram's documented `CloseStream` message and waits for the socket to close itself (flushing the final transcript) before extracting, with a 1200ms fallback so a dropped close event can't strand the contractor on "Extracting…" forever. An `intentionalCloseRef` distinguishes a user-initiated Stop/close from a real connection failure — both fire the same WebSocket `close` event, and only the latter should surface as an error; `onclose` also now logs the real close code/reason (not just the content-free `onerror` event) for any future debugging.
- **Existing-customer resolution happens client-side** (`findMatchingCustomer`/`buildInitialDataFromExtraction`), not in the LLM prompt — normalizes the extracted phone/name and matches against the already-loaded real customer list. A match sets `customerMode: 'existing'` and is *always* flagged for review regardless of what the model itself reported confidence on, since it's still a guess; no match falls back to `customerMode: 'new'` with the extracted fields populated. Keeps the real customer list out of a third-party prompt entirely.
- **`CreateJobModal` gained two optional props**: `initialData` (merged over its defaults, after any surviving sessionStorage draft — a fresh voice capture always starts a new session and shouldn't be silently overridden by old leftover draft state) and `flaggedFields`. A new `reviewFields` state + `.input-needs-review` CSS class (amber, distinct from the existing red/green invalid/valid) renders on any flagged field until the contractor actually edits it, at which point the flag clears — the concrete mechanism for "flag for manual review rather than silently guessing." - **Mic button** on Panel 1's toolbar, gated behind `canManageJobs` and a `VOICE_CAPTURE_SUPPORTED` feature-detect (`getUserMedia`/`MediaRecorder`/`WebSocket`) — disabled with a tooltip on unsupported browsers instead of the modal crashing.

## 18. Technician Onboarding: One-Time Setup Link (replaces raw-password-over-SMS)

### Why
`add-technician` (§10) originally generated a random password and sent it in plaintext over SMS/email. After researching NIST SP 800-63B-4 / OWASP guidance with the user, that was replaced with a one-time setup link: the technician taps it and chooses their own password — no password is ever transmitted over SMS, no forced-change screen is needed afterward, and a phone-number typo at creation time can no longer hand a stranger a working password. Planned in full with the user first (plan mode, `AskUserQuestion` for the open decisions) before any code was written — see the approved plan for the full research/rationale; this section covers what was actually built and verified.

**Decisions locked in with the user**: setup-link over raw password; 48-hour token expiry; a resend does **not** invalidate the previous token (both stay valid until whichever is used first); a lightweight web fallback page is built now (not deferred to the separate Flutter mobile app, which isn't in this repo); password policy is 8+ characters, no complexity rule (technicians are field workers typing on a phone).

### What was built
- **`backend/sql/008_technician_setup_tokens.sql`** — new `technician_setup_tokens` table: `technician_id`, `token_hash` (SHA-256 hex — the raw token is never stored, same principle as the temp password never being logged), `expires_at`, `used_at`, `consumed_reason` (`'completed'` / `'superseded_by_sibling'` / `'phone_changed'`), `created_by`. No RLS — every Lambda here uses the service-role key, matching this codebase's established pattern of explicit ownership checks in Lambda code rather than RLS as the boundary. **Gotcha hit while applying this migration**: PostgREST's schema cache didn't pick up the new table after the first `CREATE TABLE` run and returned `PGRST205 Could not find the table 'public.technician_setup_tokens' in the schema cache` even though `NOTIFY pgrst, 'reload schema'` was run — turned out the very first attempt's `CREATE TABLE` never actually executed (a different query ran in the SQL Editor tab), so the "cache" error was a red herring for "the table doesn't exist yet." If this resurfaces, verify with a raw `SELECT * FROM <table>;` in the SQL Editor first — a `relation does not exist` error means the DDL didn't run, not that PostgREST is stale.
- **`backend/functions/shared/technicianSetupTokens.js`** (new master helper, copied into every function folder that needs it — no Lambda Layer exists in this repo): `generateSetupToken()` (256-bit, `crypto.randomBytes(32).toString('base64url')` — entropy is the real brute-force defense, not rate-limiting), `hashToken()`, `issueSetupToken()`, `buildSetupLink()`. `SETUP_BASE_URL` is a **placeholder** (`https://app.fieldloop.io`) — no real hosting domain exists yet for the web fallback page or a future Flutter deep link; swap it once one is chosen. Once the Flutter app registers iOS Associated Domains / Android App Links on that same real domain later, this exact URL doubles as the mobile deep link with zero backend changes.
- **`add-technician`** — still generates an internal-only Auth password (never surfaced anywhere — no SMS, no email, no API response, no log) so the Supabase Auth user has *something* to authenticate with until `complete-technician-setup` overwrites it (no verified "passwordless phone user" creation path was assumed). After the `technicians` insert succeeds, issues a setup token and sends the link instead of a password. Response field renamed `credential_delivery.temporary_password` → `credential_delivery.setup_link` (still one-time-display-on-failure only, same pattern as before).
- **`resend-technician-setup`** (new, `POST /technicians/resend-setup`, owner_admin) — issues a new token **without** touching any existing unexpired one, per the explicit "both valid until one is used" decision. Refuses with a clean error if the technician has already completed setup (`password_changed = true`) — resend is meaningless past that point, checked server-side, not just hidden in the UI.
- **`complete-technician-setup`** (new, `POST /technicians/complete-setup`) — **the one Lambda in this system not authenticated via `requireContractorRole`/any JWT**; auth here is "possession of a valid, unexpired, unused token." Validates password length (8+), hashes the token, looks it up, and on success: sets the real Auth password, flips `technicians.password_changed = true` / `invite_status = 'active'`, marks the used token `consumed_reason = 'completed'`, and **invalidates every other outstanding token for that technician** (`consumed_reason = 'superseded_by_sibling'`) — this doesn't contradict the "don't invalidate on resend" rule (that's about issuance time, before anyone has acted); this is about completion time, so a second person holding an older SMS can't silently reset the password later. One generic error (`"This setup link is invalid or has expired."`) covers not-found / expired / already-used / deactivated-technician — deliberately never distinguishes which, so a second SMS recipient learns nothing about token state.
- **`update-technician`** — when `mobile_phone` changes on a technician who hasn't completed setup yet (`password_changed === false`), invalidates every outstanding token (`consumed_reason = 'phone_changed'`) and immediately issues + sends a fresh one to the corrected number. Without this, fixing a phone-number typo would leave the *original* (wrong-number) recipient holding a fully valid setup link — a real account-takeover path, not just a UX nit.
- **`list-technicians`** — now also selects `password_changed`, so the roster can decide when "Resend setup link" is relevant.
- **Web fallback page** (`src/technician-setup/TechnicianSetupPage.jsx`, new route `/technician-setup` in `src/App.jsx`) — unauthenticated, standalone (no dashboard chrome), reads `?token=` from the URL, lets the technician set + confirm a password, calls `complete-technician-setup` directly via a new unauthenticated `api.completeTechnicianSetup()` (plain `fetch`, not `authFetch` — no session exists at this point). This is what makes the feature usable *today*, independent of the separate Flutter app's timeline; the same URL becomes the mobile deep link later with no backend change.
- **Dashboard UI** (`ContractorCommandDashboard.jsx`) — `modalNotice` banner and `AddTechnicianModal`'s success/failure copy changed from "Temporary Credentials"/password language to "Setup Link" language; roster actions gained a "Resend setup link" button (gated by `canManageTechnicians` **and** `password_changed !== true` — disappears once setup is done).

## 19. Messaging Abstraction Adapter ($0-cost Phase 1 messaging)

### Why — external directive received, and what needed correcting
The project owner forwarded a technical directive (drafted with Gemini's help, addressed to the Jenex engineering team) mandating a **messaging abstraction adapter**: client-facing message delivery (technician setup links today; estimates/change-orders/invoices once those exist) should route through email or a console/log simulation during Phase 1 development, with a single config flag flipping to real Twilio SMS at launch — so no telecom cost or A2P 10DLC compliance wait blocks development, and no business logic gets rewritten when going live.

The core pattern is sound and was adopted, but the directive as written doesn't match this codebase and needed correcting before being treated as literal instructions for this repo:
- It describes **"a Python microservice on AWS Lambda."** Every Lambda in this project is **Node.js 20.x** — there is no Python anywhere in this stack. If forwarded as-is to whoever writes the code, this would have led to a mismatched/duplicate service.
- It describes a separate **"MessagingAdapter microservice."** This project has no microservice layer distinct from Lambda + API Gateway (§2/§5) — there isn't even a Lambda Layer (`backend/functions/shared/` is copied per-function by hand). The adapter had to be built as exactly that: one more `shared/` helper, copied into each function folder that uses it, same as every other cross-cutting concern here.
- **A rougher version of the $0-cost fallback already existed** before this directive arrived: `add-technician`/`update-technician`/`resend-technician-setup`'s `sendSms`/`sendEmail` helpers already gracefully no-op (returning `delivered: false` + a `reason`) whenever the `fieldloop/twilio-credentials`/`fieldloop/ses-credentials` secrets don't exist — which they still don't (§10). That's functionally close to a `dev_log` mode already, just informal, undocumented as a reusable pattern, and duplicated three times instead of centralized.
- The directive's suggestion to log simulated sends into "the Supabase Audit Table" was **not** followed — `access_audit_log.action` has a tightly verified `CHECK` constraint (only `'update'`/`'view'`/`'reveal'`/`'delete'`/`'export'`, confirmed via probe-insert in an earlier session, §12) that a message-simulation log has no business being forced into. A new dedicated table (`simulated_messages`) was used instead.
- The directive's instruction to "keep Twilio SID/Auth Token unpopulated until go-live" was **already true**, unprompted — `fieldloop/twilio-credentials` has never existed in this project's Secrets Manager.

### What was built
- **`backend/sql/009_simulated_messages.sql`** — new table backing `dev_log` mode: records what *would* have been sent (provider mode, channel, destination, subject/body) without actually sending anything. Kept deliberately separate from `access_audit_log` for the reason above.
- **`backend/functions/shared/messagingAdapter.js`** (new master helper) — the actual provider-adapter. One function, `sendMessage(supabase, { preferredChannel, phone, email, smsBody, emailSubject, emailHtml })`, routes based on a `MESSAGING_PROVIDER` Lambda environment variable:
  - **`dev_log`** — never sends anything real; inserts a row into `simulated_messages` and returns `delivered: true, simulated: true`.
  - **`dev_email`** (the directive's stated **Phase 1 default**) — routes *everything* through real AWS SES email, **regardless of `preferredChannel`** — the whole point being that an Alpha tester (e.g. the Luxe Renovation SRQ field trial mentioned in the directive) actually receives something on a real device at $0 telecom cost, not just an admin-facing "here's the link" fallback banner. Fails gracefully (not an error) if the recipient has no email on file — a real, known limitation for technicians specifically, see below.
  - **`prod_sms`** — real production behavior, byte-for-byte identical to what `add-technician`/`update-technician`/`resend-technician-setup` already did before this adapter existed: honors `preferredChannel` (SMS via Twilio if that's what was chosen, email via SES if that's what was chosen), falling back to whichever destination is actually available.
  - The Twilio/SES calling code itself (raw `fetch` to Twilio's REST API; `@aws-sdk/client-ses`) was moved here verbatim from the three Lambdas that used to each have their own copy — this is a real deduplication, not just a wrapper.
- **Retrofitted `add-technician`, `update-technician`, `resend-technician-setup`** to call `sendMessage()` instead of their own local `sendSms`/`sendEmail` — each Lambda lost ~80 lines of duplicated Twilio/SES logic.
- **`MESSAGING_PROVIDER=dev_email`** set as a Lambda environment variable on all three functions, matching the directive's stated Phase 1 default.

### Known limitation, stated plainly rather than glossed over
`dev_email` mode's practical value for **technicians specifically** is limited to technicians who have an email address on file — a technician's real identity is phone-only (§10/§11), and email is optional unless the contractor explicitly chooses email as the delivery channel. For a phone-only technician, `dev_email` mode has no destination to deliver to and falls back to the existing "shown once in the admin UI" behavior — which is correct/expected, not a bug, but worth knowing this pattern shows its full intended value once Estimates/Invoices exist (§7 — still 100% mock data), where a customer's email is much more reliably on file alongside their phone.

### What was tested (real, live — all three provider modes, all three retrofitted Lambdas)

## 22. FieldLoop AI Knowledge Base — real fact-based retrieval system, built, deployed, live data (2026-08-10)

Full design rationale, open questions, and the client's direct answers live in `Fieldloop Docs\FieldLoop_KB_Technical_Design.md` (a sibling folder to this repo, not inside it) — this section is the HANDOFF.md-side summary of what's actually running.

**Why the pilot was retired, not extended**: the real content format (atomic single-fact rows, a trade → subcategory → category hierarchy, `topic_tags`) diverged from the pilot's shape (loose `trade`/`category`/`topic`/`answer` text fields) more than it converged. `013_retire_estimate_knowledge_base.sql` dropped the old table — only 3 disposable test rows existed, zero real data lost. The 3 old Lambdas (`create-kb-entry`/`list-kb-entries`/`review-kb-entry`) were left deployed in AWS, idle — nothing calls them anymore since `KnowledgeBasePanel.jsx` and its `api.js` methods were removed from `RegistrationDashboard.jsx` — rather than torn down, matching this repo's preference for reversible steps over deleting deployed infrastructure.

### 22.1 Schema (`012_kb_fact_system.sql`)

`kb_trades` → `kb_subcategories` → `kb_categories` → `kb_entries`. Each `kb_entries` row is one atomic fact: `fact_title`, `fact`, `topic_tags text[]`, `source_type`, `verify_locally` (a boolean caveat flag — some facts vary by local jurisdiction/code and need to say so), `embedding vector(1536)` + `embedding_model_version`, `status` (`pending`/`approved`/`rejected`/`superseded`), `version`/`previous_version_id`. `search_text` is a plain column (not a generated column — see the gotcha below) kept current by a `BEFORE INSERT OR UPDATE` trigger, indexed with GIN for full-text search; `embedding` is indexed with HNSW for vector similarity. `match_kb_entries()` is a Postgres RPC function combining both (hybrid search).

**Real Postgres gotcha hit and fixed**: `search_text tsvector GENERATED ALWAYS AS (to_tsvector(...)) STORED` fails (`42P17: generation expression is not immutable`) because `to_tsvector(regconfig, text)` is `STABLE`, not `IMMUTABLE`, in Postgres's own catalog — generated columns require immutability. Neither a `LANGUAGE sql IMMUTABLE` wrapper (gets inlined by the planner, re-exposing the real `STABLE` call) nor a `LANGUAGE plpgsql IMMUTABLE` wrapper fixed it. Final fix: a plain column populated by a `BEFORE INSERT OR UPDATE` trigger instead, which has no immutability restriction.

### 22.2 Retrieval Lambdas

- **`search-kb-entries`** (`POST /kb/search`) — the ask-a-question endpoint. Dual auth (contractor JWT via `requireContractorRole`, tried first; technician JWT via the new `requireTechnicianAuth`, tried second — see §5's shared-helpers list). Flow: embed the question (OpenAI `text-embedding-3-small`, raw `fetch`, no SDK — matching `voice-extract`'s existing pattern) → `match_kb_entries` RPC (hybrid vector+text search) → **confidence gate**: similarity ≥ threshold returns the top fact directly, zero LLM cost (`source: 'retrieval'`); below threshold escalates to one grounded `gpt-4o-mini-2024-07-18` completion restricted to the top 3–5 retrieved facts, which either synthesizes an answer from them or honestly says it doesn't know — **never invents beyond what was retrieved** (`source: 'llm_escalation'`); nothing retrieved at all returns `source: 'no_match'`. **Confidence threshold recalibrated from an initial 0.82 down to 0.70** after real testing showed genuinely correct matches scoring 0.63–0.78 — the original threshold was escalating to the LLM even on clean, already-correct retrieval hits.
- **`list-kb-trades`** (`POST /kb/trades`) — discovery endpoint, same dual auth, returns `{ trades: [{ slug, name, subcategories: [{slug, name}] }] }`. Built specifically so the mobile app can look up valid slugs to pass into `/kb/search` without hardcoding them — this gap was found while reviewing `MOBILE_TEAM_HANDOFF.md`, which had claimed no technician-facing retrieval endpoint existed at all despite one already being built the same session.

### 22.3 Import/approve tooling (`backend/scripts/`, not Lambdas)

### 22.4 Trade partitioning (`014_kb_entries_partition_by_trade.sql`)

The client explicitly requested, after committing to build content for all 4 launch trades, that trade segmentation be a **structural** database guarantee, not just a trusted `WHERE trade_id = ...` filter — his concern: the same term (e.g. "depth") can mean something different from one trade to another, and cross-trade term collisions in retrieval would be a real problem if that filter were ever missed. `kb_entries` is now a native Postgres `PARTITION BY LIST (trade_id)` table with one physical partition per trade (`kb_entries_concrete_and_pavers`, `kb_entries_general_contractor`, `kb_entries_roofing`, `kb_entries_insulation`) plus a `DEFAULT` partition for any future trade. **No application code changed** — every consumer (`search-kb-entries`, `list-kb-trades`, the import/approve scripts) references `kb_entries` by name exactly as before; Postgres transparently routes to the correct partition.

**The migration took two real attempts.** The first — `ATTACH PARTITION` on the existing, already-populated table (metadata-only, no data copy) — failed identically four times with `42804: child table is missing constraint "kb_entries_status_check[1]"` despite several different fixes to the child table's CHECK constraint; the exact constraint-matching mechanics of `ATTACH PARTITION` were never fully pinned down, and guessing further against live production data (500 real rows) wasn't worth continuing. The approach that worked: rename the existing table to `kb_entries_old` (kept as a manual-rollback backup, not dropped), build the new partitioned structure fully empty with every partition created fresh via `CREATE TABLE ... PARTITION OF` (which reliably auto-inherits all parent constraints, unlike `ATTACH`), then copy the 500 rows across with a plain `INSERT ... SELECT`. Two smaller gotchas along the way: a self-referencing FK had to be dropped before the PK it depended on (`2BP01`), and index names — unlike constraint/trigger names — are unique per-schema, not per-table, so the renamed backup table's original indexes needed explicit `DROP INDEX` before the new identically-named ones could be created. RLS policies were defined explicitly on the parent and every individual partition (declarative partitioning does not auto-inherit RLS — confirmed against current Postgres docs) — not a live risk today since every Lambda uses the service-role key and bypasses RLS regardless, but correct for defense-in-depth.

**Verified, not assumed**: row counts matched exactly before/after (500 in, 500 out — zero data loss); per-trade breakdown after migration was `concrete_and_pavers: 500`, `general_contractor: 0`, `roofing: 0`, `insulation: 0` (all 4 trades exist as real partitions; only concrete has content, matching where the client's authoring actually stands); and — the point of doing this at all — **partition isolation was empirically proven**: the identical question that returns a correct, high-confidence answer against `concrete_and_pavers` correctly returns `no_match` when asked against a different trade slug, confirming the segmentation is a real structural guarantee and not just a filter that happens to be applied correctly today. `kb_entries_old` remains in place as a rollback safety net, left for a manual decision on when to drop it.

## 25. Platform Overview UI/UX rework — real tabs + contractor drill-down (2026-08-13)

The first version of §24 shipped everything as one long scroll of panels — no navigation structure, no way to click into a specific contractor, revenue/usage/contractors all fighting for space on one page. The user flagged this directly ("looks very static," "no drill-down," "structure is wrong") and asked for a real design pass, not a patch — planned first (tabs/nav structure, chart approach, drill-down data/fetching, technical scope, phasing), confirmed, then built in two phases.

### 25.1 UX restructure — real tabs, reusing the existing sidebar mechanism

`ContractorCommandDashboard.jsx` already has a proven tab pattern: a numbered sidebar (`pages` array + `.page-N .section-N` CSS in `dashboard.css`, all panels always mounted, just hidden via CSS). §24's first version had accidentally discovered this CSS rule as a *bug* (everything but the KPI row was invisible) and worked around it by hardcoding `page-1`/`section-1` everywhere — this rework replaces that hardcode with the real mechanism it was always meant to be: a genuine `activeTab` state and a sidebar with 5 real tabs (**Overview, Contractors, Usage, Revenue, Knowledge Base**), each panel tagged with the section number matching its tab.

**Rationale for the grouping**: Overview is the "what needs my attention" landing view (KPI row + a compact alert strip — missing-status contractors, compliance expiring, pending KB submissions — each alert a button that jumps straight to the tab that resolves it) rather than trying to also be a full data browser. Contractors is its own tab because it's the primary workflow (browsing/searching/drilling in), not a panel fighting five others for space. Usage and Revenue were split out specifically so a genuinely-still-`$0` revenue panel doesn't visually compete with panels that do have real data. Knowledge Base keeps content-coverage and the review queue together since they're both "state of the KB."

**A real gotcha hit while testing this, not the app**: because every tab's panels stay mounted in the DOM (just `display:none`), a Playwright locator like `tr:has-text("Luxe renovation")` matched three different rows across three different tabs simultaneously (the roster table, the missing-status table, and the most-active-contractors table on the Usage tab all independently contain that contractor's name) — this is expected/correct given the architecture, not a bug, but it means any test script against this page has to scope locators to the visible tab's section (`.section-2`, etc.), the same lesson `ContractorCommandDashboard.jsx`'s own testing already learned (HANDOFF.md §9 Round 2).

### 25.2 Contractor drill-down — a real route, not a modal

`/staff/platform/contractors/:id`, gated by the identical admin-only pattern as `/staff/platform` (`PlatformContractorSection` in `App.jsx`, mirroring `PlatformSection`). Chose a route over a modal because the payload is large (profile + compliance + financials + audit log + full operational usage) and this codebase's existing convention for viewing a full record is a full page (the Registration Dashboard itself), not a modal — modals here are reserved for quick actions (Add Technician, Create Job), not record browsing. A route is also bookmarkable/shareable between staff.

**Data sourcing — one endpoint reused, one new one needed.** `get-contractor` (existing, already used by the Registration Dashboard) already returns everything profile-shaped for `admin` unmasked — contractor identity, compliance, operations, financials, meta, and the last 8 `access_audit_log` rows — reused here completely as-is, zero backend changes.
